| | ЛР6 — словники (`kzp_lab06`) | ЛР7 — об'єкти (`kzp_lab07`) |

## 3. Модель

**Базовий клас `Medicine(ABC)`** (`models.py`):

- `__init__(name, form, price, days_left)` — `self` означає створюваний екземпляр;
  значення записуються в «приватні» атрибути `_name`, `_form`, а `price` і `days_left` —
  через властивості, тобто через setter-перевірки.
- **Властивості:**

| Властивість | Доступ | Перевірка |
|-------------|--------|-----------|
| `name` | лише читання | текст, непорожній, пробіли нормалізовано |
| `form` | лише читання | текст, непорожній, нижній регістр |
| `price` | читання + setter | число (не `bool`, не рядок) → `TypeError`; скінченне й ≥ 0 → `ValueError`; зберігається як `float` |
| `days_left` | читання + setter | ціле (не `bool`, не `float`) → `TypeError`; ≥ 0 → `ValueError` |
| `prescription` | лише читання | береться з атрибута класу підтипу |
| `sort_key` | лише читання | `(days_left, name)` |

  `name` і `form` лише для читання, бо вони входять у `__eq__` та `__hash__`. Якби вони
  змінювалися, об'єкт «загубився» б у `set` чи `dict`.
- **Інваріант**: будь-який існуючий об'єкт має коректні поля. Setter відхиляє хибне значення,
  не змінюючи старого (тест `test_price_setter_rejects_invalid_values`).
- **Спеціальні методи:**
  - `__str__` → `Назол (спрей)` (саме так препарат виглядає у звіті);
  - `__repr__` → `FreeMedicine(name='Назол', form='спрей', price=60.0, days_left=14)`;
  - `__eq__` → той самий підтип, назва й форма; для чужого типу повертає `NotImplemented`;
  - `__hash__` → `hash((type(self), name, form))`.
- **Впорядкування** — через `key` (`sort_key`, `analysis.by_expiry`), а не `__lt__`. Звіт
  сортує то за терміном, то за доступністю, і для кожного порядку достатньо свого `key`,
  тоді як `__lt__` нав'язав би класу один «природний» порядок.
- `price_penalty()` — спільна частина формул підтипів (1 бал за кожні повні 10 грн, не більше 50).
- Клас абстрактний (`@abstractmethod availability_score`), тож `Medicine(...)` дає `TypeError`.

## 4. Dataclass

```python
@dataclass(frozen=True)
class Summary:
    count: int
    average_price: float
    nearest: Medicine | None
    expiring: tuple[Medicine, ...]  # препарати з близьким терміном — підсумок варіанта
    threshold: int
    forms: tuple[str, ...]
    by_form: tuple[tuple[str, int], ...]
    prescription_count: int
    total_price: float
    average_availability: float
```

- `@dataclass` генерує `__init__`, `__repr__` і `__eq__` за полями, тож не треба писати
  шаблонний код.
- `frozen=True` забороняє присвоєння після створення (`FrozenInstanceError`) і робить об'єкт
  хешованим. Колекції подано **кортежами**, щоб незмінним був і вміст, а не лише посилання.
- **Роль**: `analysis.summarize` один раз обчислює всі показники, а `reporting.format_report`
  лише читає їх. Звіт не може випадково змінити результат аналізу.

## 5. Підтипи та протокол

| | `PrescriptionMedicine` | `FreeMedicine` |
|-|------------------------|----------------|
| `PRESCRIPTION`, `LABEL` | `True`, «за рецептом» | `False`, «без рецепта» |
| `availability_score()` | `max(10, 60 − штраф)` | `100 − штраф`, ще `− 20`, якщо `days_left < 30` |
| термін спливає сьогодні | 0 | 0 |

Однакові дані «Ліки; таблетки; 100.00; 200» дають 50 і 90 (тест
`test_subtypes_score_same_data_differently`).

**Протокол** `Scored` (`typing.Protocol`, `@runtime_checkable`) описує контракт із двох
властивостей (`name`, `days_left`) і методу (`availability_score()`). Функції `analysis`
(`by_expiry`, `expiring_soon`, `average_availability`, `top_by_availability`) приймають
`Iterable[Scored]`:

```python
scores = [item.availability_score() for item in items]  # без isinstance і if за підтипом
```

Це качина типізація: важить наявність потрібних атрибутів, а не клас. Тест
`test_duck_typed_object_satisfies_protocol` показує, що й сторонній клас `Voucher` без
спадкування відповідає протоколу.

Підтип вибирається лише у фабриці `create_medicine` через словник
`SUBTYPES = {True: PrescriptionMedicine, False: FreeMedicine}`, без `if`. Новий підтип не
потребує змін в `analysis` і `reporting`.

## 6. Модулі

| Модуль | Призначення | Не робить |
|--------|-------------|-----------|
| `models.py` | класи, протокол, dataclass, фабрика | не читає файлів, не форматує звіт |
| `loader.py` | `DictReader` → перевірка формату → `create_medicine`; помилки моделі перетворює на `DataError` з номером рядка | не обчислює показники |
| `analysis.py` | відбір, сортування, середня доступність, `summarize` → `Summary` | не залежить від CLI і файлів |
| `reporting.py` | `format_report` (той самий текст, що в ЛР6), `format_details`, `atomic_writer`, `write_report` | не читає CSV |
| `errors.py` | `DataError(ValueError)` | — |
| `cli.py` | `argparse`, коди 0/1/2, stderr, `--details` | не містить предметної логіки |

**Завдання із зірочкою.** `Scored` — протокол із властивостями й методом.
`atomic_writer(path)` — власний контекстний менеджер (`@contextmanager`). Він пише в
тимчасовий файл у тому самому каталозі й лише після успішного завершення блоку `with`
атомарно замінює цільовий файл (`os.replace`). При винятку файл закривається, тимчасовий
видаляється, старий звіт лишається, а виняток іде далі. Тести
`test_atomic_writer_closes_and_rolls_back_on_exception` і
`test_atomic_writer_does_not_create_file_on_exception` перевіряють `stream.closed`, вміст і
відсутність сміттєвих файлів.

## 12. Відповіді на контрольні питання

1. **Клас і екземпляр.** Клас — опис (шаблон) з атрибутами й методами. Екземпляр — конкретний
   об'єкт, створений за цим описом, зі своїми значеннями полів (`FreeMedicine("Назол", …)`).
2. **`__init__` і `self`.** `__init__` ініціалізує новий екземпляр (задає початковий стан).
   `self` — посилання на цей екземпляр, через нього метод звертається до атрибутів об'єкта.
3. **`@property`.** Перетворює метод на атрибут для читання. Разом із setter-ом дозволяє
   перевіряти значення під час присвоєння, а синтаксис доступу лишається простим (`m.price`).
4. **Чому setter пише у внутрішнє поле.** Присвоєння `self.price = value` всередині setter-а
   знову викликало б той самий setter, і рекурсія була б нескінченною. Тому значення
   зберігається в `self._price`.
5. **Що додає `@dataclass`.** `__init__` з полями, `__repr__`, `__eq__` за значеннями полів, а
   також за параметрами `order`, `frozen` тощо — порівняння й незмінність.
6. **`frozen=True`.** Забороняє змінювати поля після створення і робить об'єкт хешованим.
   Підсумок стає «значенням», яке можна безпечно передавати й зберігати.
7. **`__str__` і `__repr__`.** `__str__` — зрозуміле подання для користувача (`print`, f-рядок).
   `__repr__` — однозначне подання для розробника, бажано таке, з якого можна відтворити об'єкт.
8. **`__eq__` з несумісним типом.** Має повертати `NotImplemented`, щоб Python спробував
   порівняння з боку іншого об'єкта. Якщо й там не визначено, результат — `False`. Кидати
   виняток неправильно.
9. **`key` проти `__lt__`.** `key` кращий, коли потрібно кілька різних порядків (за терміном, за
   доступністю) або коли порядок не є природною властивістю об'єкта. `__lt__` фіксує один
   «природний» порядок.
10. **`super()`.** Дає доступ до методів батьківського класу з урахуванням MRO, наприклад щоб
    у підтипі викликати конструктор базового класу. У нас підтипи не мають власного
    `__init__`, тож конструктор `Medicine` успадковується без змін.
11. **MRO.** Method Resolution Order — порядок пошуку атрибутів у класах ієрархії
    (`type.__mro__`). Він важливий при множинному спадкуванні та для `super()`, бо визначає,
    чий метод буде викликано.
12. **Качина типізація.** Важить не клас об'єкта, а наявність потрібних методів і атрибутів:
    «якщо ходить як качка й крякає як качка — це качка».
13. **Що дає Protocol.** Формально описує контракт для качиної типізації без спадкування.
    Статичний аналізатор перевіряє відповідність, а з `runtime_checkable` її можна
    перевірити й через `isinstance`.
14. **Чому analysis не перевіряє підтипи.** Інакше кожен новий підтип вимагав би змін у
    кожній функції. Поліморфний виклик тримає правило поруч із даними, у класі.
15. **Де перетворювати словник на об'єкт.** У loader — на межі між зовнішніми даними та
    моделлю. Далі весь код працює лише з перевіреними об'єктами.
16. **Чому модулі не запускають CLI під час імпорту.** Імпорт (у тестах, в іншому модулі) не
    повинен мати побічних ефектів: читати аргументи, писати файли чи завершувати процес.
    Запуск — лише в `if __name__ == "__main__"`.
17. **Які властивості об'єктів перевіряються тестами.** Коректні значення властивостей,
    відхилення хибних setter-ом без зміни стану, лише читання для ключових полів,
    рівність/хеш, рядкові подання, формули підтипів і межі, незмінність dataclass.
18. **pytest, ruff і wheel.** pytest перевіряє поведінку, ruff — стиль і підозрілий код, wheel —
    що пакет правильно збирається й ставиться в чисте середовище з робочою командою.
19. **Крайові випадки.** Порожній файл і лише заголовок, дублікати, межові значення порогу й
    формул (0, 29/30, 30/31, стеля штрафу), хибні типи й значення в setter-і, пошкоджені рядки,
    відсутній файл, вхід = вихід, виняток під час запису звіту.
20. **Що задекларувати в REPORT.** Класи, поля й операцію варіанта, приклад CSV і повний звіт,
    доказ сумісності з попередньою роботою, коди завершення, результати pytest/ruff/wheel/CI з
    посиланнями, версію й тег, використання ШІ.

## 13. Висновки

Застосунок перебудовано на об'єктну модель. Препарат інкапсулює свої дані та правила
(`@property` з перевірками), підтипи мають власні формули спільної операції, аналіз працює
через протокол без розгалужень за класом, а підсумок — незмінний dataclass. Зовнішній звіт
доведено ідентичний ЛР6. Нова поліморфна можливість (`--details`) додана, не зачіпаючи
стандартний вивід.

Основою для подальшої роботи стали модульна структура `models → loader → analysis →
reporting → cli`, протокол як точка розширення (новий підтип не змінює аналіз і звіт),
безпечний запис файлів і повна перевірка в CI на трьох ОС.
